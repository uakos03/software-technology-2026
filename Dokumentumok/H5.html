Főoldal

Objektumtervezés, implementáció és tesztelés

  1. A rendszer vezérlésének kidolgozása
    • 1.1 Architektúra

      A szoftver megtervezése során kiemelt figyelmet fordítottunk arra, hogy egy modern, átlátható és jól karbantartható rendszert hozzunk létre. A rendszer az étterem hálózatán kliens-szerver felépítésben működik. A felhasználókkal közvetlenül érintkező kliens egy Tauri-ba csomagolt React alkalmazás, míg a háttérben egy Spring Boot alapú Java szerver dolgozik, amely egy PostgreSQL adatbázisban tárolja az adatokat. A szerver kialakításánál a klasszikus, egyetemen is tanított háromrétegű (3-tier) architektúrát követtük. Ez a felelősségek szétválasztásának elve alapján biztosítja, hogy a kódunk ne legyen átláthatatlan spagettikód.

      RétegFelelősségPélda osztály
      ControllerA legkülső réteg. Fogadja a kliens felől érkező HTTP kéréseket, ellenőrzi az alapvető bemeneti adatokat, majd továbbítja a feladatot a belső rétegeknek.RendelesController
      ServiceA rendszer „agya”. Itt kap helyet a tényleges üzleti logika (például a raktárkészlet kiszámolása, jogosultságok kezelése), és ez a réteg irányítja a folyamatokat.RendelesService, KeszletService

    • 1.2 Fő folyamatok vezérlése

      A fejlesztés megkezdése előtt tisztáznunk kellett, hogy a felhasználói felületről érkező kérések hogyan haladnak végig a szerver különböző rétegein. A leggyakoribb és legkritikusabb folyamat a rendelés leadása. Az alábbi táblázat lépésről lépésre bemutatja azt az üzenetváltást, amely egy egyszerű gombnyomás mögött a háttérben lezajlik az objektumok között:

    • 1.3 Az állapotgépek megvalósítása

      Az éttermi munkafolyamatok során a rendelések (például Nyitott, Lezárt) és a tételek (például Konyhán, Kész) különböző állapotokon mennek keresztül. Az Analízis modell szerint az állapotátmeneteket maguk az osztályok műveletei végzik (például a Rendelés_tétel sztornozas, a Kiszállításos_rendelés indulas művelete), ezért az entitásokban felsoroló típusú, úgynevezett Enum mezőket hoztunk létre, a Service osztályok pedig ezeket a műveleteket hívják. Ha például egy pincér olyan műveletet akar végezni, ami az adott állapotban logikátlan (mondjuk egy már kifizetett és lezárt rendeléshez akar új italt hozzáadni), az entitás hibát jelez, a Controller pedig a felületen egy barátságos, magyar nyelvű hibaüzenet formájában jelzi a felhasználónak. A vevő és az asztal állapotát nem tároljuk, hanem a mezőkből számoljuk.

Ennek előnye, hogy nem kell hosszú, bonyolult SQL parancsokat írnunk, hanem a Java objektumainkat használhatjuk.

  3. Elemzési modellek modulokba szervezése
    • 3.1 Szerveroldali modulok

      Egy ekkora projekt esetében a kód átláthatósága és a fejlesztők közötti munkamegosztás kritikussá válik. Ha minden fájlt egyetlen nagy mappába tennénk, a projekt kezelhetetlen lenne. Ezért a Java kódot logikai csomagokba (package) szerveztük a funkciók alapján. Ez a moduláris felépítés lehetővé teszi, hogy ha a későbbiekben módosítani kell például a pénzügyi részt, az ne tegye tönkre a rendelésfelvételt.

      • rendeles: Ebben a csomagban van minden osztály, ami a rendelésekkel és asztalok kezelésével kapcsolatos.
      • etlap: A termékek, alapanyagok, receptúrák és a raktárkészlet kezeléséért felelős fájlok mappája.
      • felhasznalo: A dolgozók azonosításához és a kiszállításos vevők nyilvántartásához szükséges osztályok.
      • penzugy: A fizetési tranzakciók, nyugták generálása és a napi zárás folyamatai találhatók itt.
  4. Implementáció (Skeleton)
    • 4.1 A prototípus (Skeleton) hatóköre

      Az egyetemi projekt keretein belül nem valósítjuk meg a teljes rendszert. A megírt váz (skeleton) egyetlen úgynevezett hibamentes folyamatot tud végigvinni:

      1. A felhasználó sikeresen belép.
      2. Látja a szabad asztalokat, kiválaszt egyet.
      3. Tételeket rak a kosárba és leadja a rendelést.
      4. A tételek megjelennek a Konyhai (szakács) nézeten.

      A többi funkció (pl. kiszállítás, e-mail küldés, komplex statisztika) a prototípusban csak a felület szintjén, "csonkként" (stub) jelenik meg. Ezek a gombok és menük láthatók, de a tényleges háttérlogika még nincs hozzájuk kifejlesztve.

    • 4.2 Példa a kódvázra (Java Spring Boot)

      Az alábbi kódrészlet a backend legfontosabb folyamatát, a rendelés leadásának szerveroldali vázát mutatja be. Jól látható rajta a dokumentumban korábban vázolt réteges architektúra (Controller → Service → Repository) tényleges megvalósítása: 

      @RestController
@RequestMapping("/api/rendelesek")
public class RendelesController {

    @Autowired
    private RendelesService rendelesService;

    // Új rendelés felvétele a pultról vagy asztaltól
    @PostMapping("/leadas")
    public ResponseEntity<?> rendelesLeadasa(@RequestBody RendelesDto orderDto) {
        try {
            rendelesService.ujRendeles(orderDto);
            return ResponseEntity.ok().build();
        } catch (KeszletHianyException e) {
            // Ha nincs elég alapanyag, a frontend megkapja a hibaüzenetet
            return ResponseEntity.badRequest().body(e.getMessage());
        } catch (Exception e) {
            return ResponseEntity.internalServerError().build();
        }
    }
}

@Service
public class RendelesService {

    @Autowired
    private RendelesRepository rendelesRepository;
    @Autowired
    private KeszletService keszletService;
    @Autowired
    private KdsErtesito kdsErtesito;

    @Transactional
    public void ujRendeles(RendelesDto dto) throws Exception {
        
        // 1. Készlet ellenőrzése és azonnali levonása
        keszletService.keszletLevonas(dto.getTetelek());

        // 2. Rendelés összeállítása és DB mentés
        Rendeles rendeles = new Rendeles();
        rendeles.setAsztalId(dto.getAsztalId());
        rendeles.setStatusz(RendelesStatusz.KONYHAN);
        // TODO: MapStruct vagy külön mapper osztály használata a DTO átalakításra
        rendeles.setTetelek(dto.getTetelek()); 
        
        rendelesRepository.save(rendeles);

        // 3. Konyhai kijelző (KDS) frissítése WebSocketen
        kdsErtesito.ujBlokkKuldese(rendeles);
    }
}
  5. Tesztelési terv és tesztesetek
    • 5.1 Tesztelési stratégia

      A szoftver megbízhatóságának és minőségének biztosítása érdekében többszintű tesztelési stratégiát alkalmazunk. Nem elegendő csupán a felületet kattintgatni; a rendszer magját jelentő backend üzleti logikát (például a végösszeg pontos kiszámítását vagy az asztalok állapotának váltását) automatizált egységtesztekkel (JUnit) ellenőrizzük a kódban. A felhasználói felületet, a gombok működését és az átfogó folyamatokat pedig manuális rendszertesztekkel próbáljuk ki a kliensalkalmazás futtatásával.

Ezek a tesztek biztosítják, hogy a rendszer a leggyakoribb helyzetekben és a legáltalánosabb hibák esetén is a specifikációnak megfelelően viselkedjen:
